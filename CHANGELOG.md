# Changelog

All notable changes to this project will be documented in this file.

## [Unreleased]

The declarative-agent platform moved to
[korps](https://github.com/EmilLindfors/korps) on 2026-08-17, and is now the
`korps` and `korps-fleet` crates. Unreleased entries that were only about
`a2a-agents` went with it, into that repo's root `CHANGELOG.md`; entries
touching a protocol crate as well are in both, and keep the `a2a-agents` tag
they were written with. Released sections below are untouched.

### Added

- **A provider says whether the model refused its reasoning parameter (`a2a-llm`)**: `LlmProvider::reasoning_refused() -> Option<bool>`, defaulting to `None` ("nothing to report"), overridden by `OpenAiProvider` and `GeminiProvider` to read the refusal they already remember. Until now that memory was private: the adapter recognized the 400, retried without the parameter, logged one line and dropped the setting for the rest of the process, and nothing outside it could learn that a configured `reasoning` was being paid for and not delivered. Found from downstream — korps' status route reports an agent as degraded when it is answering without the reasoning its config asked for, and needed something to ask.

- **BREAKING — a context refusal carries the provider's numbers (`a2a-llm`)**: `LlmError::ContextLengthExceeded` carried one `String` — the formatted error body — so the two facts a caller most wants were discarded into prose: the window the provider enforced and the prompt tokens it counted. It is a struct variant now, `{ detail, prompt_tokens: Option<u32>, context_window: Option<u32> }`, and classification reads the numbers from the **raw** body before anything is flattened: llama.cpp's `n_prompt_tokens`/`n_ctx` JSON fields (root or inside the `error` object), then the two prose shapes the fixtures pin — OpenAI's "maximum context length is N" (the window) and Gemini's "input token count (N)" (the count). A shape with no fixture is not parsed: a wrong number is worse than none, because these values are what a caller repairs its config with.
  - **Found from downstream**: korps' `CeilingWatch` reports the *estimated* size of a refused request and advises setting the ceiling below it — a bound with the estimator's error on it. Measured against llama.cpp at `n_ctx = 32768`, a request estimated at 51483 tokens was 40089 by the server's count, so the advice left every value from 33k to 51k still failing, while the right answer sat unread in the error body. The same fields let korps' `DriftWatch` finally sample refused requests, the one place estimator error has a visible cost.
  - `classify_api_error` now also owns the `{label} ({status}): {body}` format, which had been written identically at all four call sites — the classification takes the raw body because the numbers must be read before formatting destroys the JSON.
  - `u32` to match `TokenUsage::prompt_tokens`, and `None` must not read as zero, on `TokenUsage`'s own rule.

- **The reasoning text is documented as the model's to give (`a2a-llm`)**: Gemini via OpenRouter bills `reasoning_tokens` on every request and put a summary in `delta.reasoning` on about one request in nine in korps' probes, with `reasoning.effort`, `enabled`, `stream_options` and no parameter at all making no difference. The parsing was right; there is usually nothing in the field. `Reasoning` and `LlmResponse::reasoning` now say so, and name `TokenUsage::reasoning_tokens` as the signal that can be relied on — so nobody builds a feature on the text arriving.

- **BREAKING — `remember` says what the key held (`a2a-rs`)**: `AsyncContextStateStore::remember` returned `Result<(), A2AError>`, so a value replaced in place left no trace anywhere. An agent that overwrote `user:name` with the wrong thing lost what it held and nothing could say it had happened — the row is overwritten, and `context_state.updated_at` records that *something* changed, not what. It now returns `Remembered`.
  - **Four answers, not a `bool` and not an `Option<String>`.** `Stored` for a key that held nothing, `Replaced { previous }` carrying the value nothing else records, `Unchanged` for a key that already held exactly this, and `NotStored` for a `temp:` key or for `NoContextState`. `Unchanged` is what keeps an agent re-asserting a fact it was told several turns ago from reading as a clobber, and `NotStored` is the answer an `Option<String>` cannot give: `None` there would mean "stored, over nothing" and "stored nowhere at all" at once. This is the same argument `forget`'s bool already carries.
  - **The sqlx store reads the old value in the same transaction as the write.** Without one, a concurrent write landing between the read and the upsert makes `previous` name a value this call never overwrote — a report about somebody else's write wearing ours. Two statements, because neither dialect hands back the old row: PostgreSQL 17's `RETURNING OLD.value` is too new to require, and the `WITH prev AS (…) … RETURNING (SELECT …)` form it would take on PostgreSQL has no SQLite spelling. The in-memory store gets it free from `HashMap::insert`.
  - Where an overwrite is *shown* is a caller's decision, and the caller here is korps' `remember` tool. This is the half that makes it possible.

- **Reads can keep a `user:` bag alive — `ReadRefresh` (`a2a-rs`)**: retention measures idleness from writes, deliberately, because a read that recorded itself would be a write per turn. The cost was a `user:` fact the model reads every turn and rewrites never: it expired under a running agent, which forgot something it was visibly using. `ReadRefresh` buys the fact back without paying that write.
  - **A window, not a flag.** A read refreshes the bag only once it is already `after` old, so however often it is read the extra writes are bounded at one per principal per window. `ReadRefresh::halfway_through(&policy)` takes that window from the `RetentionPolicy` a sweep will run under, so an operator names one number rather than two that have to be kept in step.
  - **The rule is in the domain, next to `RetentionPolicy`**, for the reason the policy is: two stores deciding separately what keeps a bag alive would be two retention rules wearing one name. Both adapters read the same value, in the two shapes they need — the SQL store binds `cutoff` into a statement, the in-memory store asks `due` about a timestamp it already holds.
  - **The principal, not the context, and not the key.** A context in use is written to by its own task history, so its idleness maintains itself; and a bag that expires a key at a time remembers somebody's city and not their name, which reads to a model as fact rather than as absence.
  - **The SQL side writes blind.** One conditional `UPDATE` matching on the primary key's `(scope, scope_key)` prefix, which usually touches nothing and leaves no dead tuple when it does not. Reading `updated_at` first to decide would be cheaper in writes and impossible in practice: it is a `timestamptz`, the `Any` driver cannot decode one, and it converts a row whole — so selecting it alongside the bag would fail every `load_state` on PostgreSQL.
  - Off by default on both stores (`ReadRefresh::never`), so a store that is not told otherwise behaves exactly as it did. `SqlxStorageBuilder::read_refresh` and `InMemoryTaskStorage::with_read_refresh` turn it on.

- **`reasoning` reaches OpenAI and Gemini (`a2a-llm`)**: `[llm] reasoning` only ever went on the wire for `openrouter`. The other two providers dropped it and said so — `SelectedLlm.reasoning` carried `ReasoningPlan::Unsupported` and `korps doctor` warned — which kept the bill from being a surprise but left the setting doing nothing on two of the three providers. Both send it now, each in its own dialect: OpenAI's `reasoning_effort` string, and Gemini's `generationConfig.thinkingConfig`.
  - **Whether a *model* takes the parameter is sent and found out, not looked up.** `reasoning_effort` is a 400 on `gpt-4o-mini` and mandatory on `gpt-5-pro`; Google's model table lists `thinkingLevel` for the 2.5 generation and the field reports say those models refuse it. A table of model names answers for the models it lists and is wrong about every one released after it was written — this entry had already gone stale once. So the parameter goes on the request, a refusal is recognized from the 400 that names the field, and the request is retried once without it. Nothing was generated on a 400, so that costs a round trip and no tokens.
  - **The refusal is remembered per provider**, so only the first call pays it — and only once the retry has succeeded, since a 400 naming the field can still be about something else and disabling reasoning for the rest of the process over an unrelated failure would be worse than the round trip.
  - **The mappings.** OpenAI: `off` → `none` (which only gpt-5.1 and later accept; an older model refuses it, and a model that does not reason satisfies "off" anyway), and the named levels as themselves. Gemini: a level for each named effort, `thinkingBudget` for a token cap, and `thinkingBudget: 0` for off, which is the documented way to turn thinking off where a model allows it. `thinkingLevel` and `thinkingBudget` are mutually exclusive and exactly one is ever set.
  - **A token budget on OpenAI is the one drop still known before the call.** Chat Completions has no reasoning-token cap field at all, so `reasoning = 2000` stays `ReasoningPlan::Unsupported` there and `korps doctor` still warns before anything is billed. Gemini has `thinkingBudget` and takes it.
  - **New `ReasoningPlan::Attempted`** for the state a recovery shape creates: configured, sent, and answered by the model rather than by selection. `unsupported()` no longer fires for a level on OpenAI or Gemini — that warning would now be about a setting that most likely works — and `attempting()` is the new one, for a report that wants to say "not known until it runs".
  - **BREAKING**: `OpenAiConfig::supports_reasoning: bool` is now `reasoning_dialect: ReasoningDialect` (`OpenRouter` | `OpenAi`), because "does it take a reasoning parameter" and "which one" stopped being the same question. `GeminiConfig` gains `reasoning: Option<Reasoning>`, matching what `OpenAiConfig` already had. Nothing constructs either by literal outside this crate.
  - A local OpenAI-compatible server (Ollama, vLLM, llama.cpp) is on the `OpenAi` dialect too, so it now gets `reasoning_effort` when a config asks for reasoning. It used to get nothing, on the grounds that a server rejecting an unknown parameter fails the whole call — which is the case the recovery handles. Nothing changes for a config that asks for no reasoning: nothing is sent either way.

- **Stream resumption can outlive the process — the `AsyncEventLog` port (`a2a-rs`)**: the ids a client resumes by came from a counter inside `InMemoryStreamingHandler`, so a restart started every task at 1 again and handed a reconnecting client ids it had already seen. Ids and retained events are now a port of their own, and `SqlxTaskStorage` implements it, so resumption survives a restart on a database-backed server.
  - **The split is fan-out versus log.** `StreamingFanout<L>` keeps the in-process half — the broadcast channel and the callback subscribers, which a restart is entitled to forget — and delegates ids and replay to the `AsyncEventLog` it was built over. `InMemoryStreamingHandler` is now `StreamingFanout<InMemoryEventLog>`, unchanged for callers: same name, same `new()`, same behaviour within one run.
  - **Migration 007 adds `task_events`**, keyed `(task_id, id)`. The id is computed inside the insert (`COALESCE(MAX(id), 0) + 1 … RETURNING id`) rather than read first and bound, so two writers racing for the same id collide on the primary key instead of both claiming it. No foreign key to `tasks`: the two are separate ports and need not be one database, and an append that failed because the task row had not landed yet would drop an event on the one path whose job is not to drop events. A retention sweep of the context deletes them instead.
  - **`SqlxStorageBuilder::event_log_capacity`** caps a task's retained events, defaulting to 1024 — four times the in-memory ring, since rows are cheaper than process memory. The oldest are trimmed as new ones arrive; `None` keeps everything.
  - **A resume the log cannot cover now streams live rather than a fragment.** `Replay::complete` says whether the log still holds every event after the requested id. When it does not, the tail that is left starts partway through the gap, and replaying it re-applies updates older than the task snapshot the service already sent — which for an appending artifact duplicates content. The fan-out drops it and streams live instead.
  - **The fan-out locks per task, not globally.** One `Mutex` over the whole task map used to be held across a callback subscriber's `await`; with a database-backed log it would have been held across a write too, serializing every broadcast on the server. The map lock now only hands out a task's channel, and the log write and the send happen under that task's own lock — still ordered against each other, which is what keeps ids and delivery in the same order.
  - **Dropping a task's subscribers no longer drops its events.** `remove_task_subscribers` cleared the replay buffer with the channel, which threw away exactly what a client was about to reconnect for. Deleting events is `AsyncEventLog::discard` now, and a sweep is what calls it.

- **ConnectRPC streams can be resumed too (`a2a-rs`)**: `subscribe_to_task` on the ConnectRPC transport ignored its `last_event_id` argument and tagged every event `None`, so `RetryingTransport` over it reconnected from the task's current state and dropped whatever arrived while the connection was down — the JSON-RPC and REST transports have replayed the gap since 0.6. Both now behave the same, and the shared `transport::resume` module is the one place the wire details live.
  - **The `Last-Event-ID` header works unchanged.** ConnectRPC is HTTP, so the client sends the same request header the SSE transports use and the server reads it off the ConnectRPC request context. `parse_last_event_id` moved out of the JSON-RPC adapter so both read it identically.
  - **The id comes back in the update's `metadata`, under `a2a_rs_event_id`.** ConnectRPC has no SSE `id:` field and `StreamResponse` is a bare payload oneof, so there is nowhere protocol-level to put it. That makes it a change to the payload rather than an inert protocol field — which is why the server stamps it **only** for a client that asked with the `a2a-rs-event-ids` request header, and why our client strips the key again before the event reaches the caller. A client that does not ask gets the bytes the spec describes.
  - Asking is per-subscription rather than per-reconnect: resuming needs the id of the last event received *before* the drop, so ids have to be flowing from the first event. Both streaming methods stamp, so a client that reads `SendStreamingMessage` can resume onto `SubscribeToTask`.
  - The id is written as a **string**. `google.protobuf.Struct` numbers are doubles and an event id is a `u64`; a number would round past 2^53.

- **An MSRV job pins CI to the declared `rust-version`**: cargo never checks `rust-version` against the dependency graph — it errors when the *toolchain* is below a dependency's floor, never when the declared number is — so the claim was true only while stable happened to be 1.96. Stable is 1.98 now, and a `dtolnay/rust-toolchain@1.96` job running `cargo check --workspace --all-features --locked` is what keeps it true. Library targets only: the dev-dependencies behind `--all-targets` have their own floors and would raise ours for nobody's benefit. The workspace does build on 1.96 as declared; nothing had to move.

- **An agent can be told to remember a fact — `[handler.llm.context] remember` (`a2a-rs`, `a2a-agents`)**: `contexts.state` had been a column since 0.5 that nothing read or wrote. The conversation is what was *said*; this is the handful of facts worth keeping apart from it, and the difference that matters is compaction — a summary can lose a detail, a stored value cannot. `remember = true` gives the model `remember(key, value)` and `forget(key)`, and puts what it kept into every later prompt. Off by default: two tools and a block of prompt change what an existing agent costs and how it answers.
  - **The key's prefix is its lifetime**, taken from Google ADK rather than invented here: `user:tone` is filed under the authenticated principal and read back in *every* conversation with that caller, a bare key belongs to the one `contextId`, and `temp:` is stored nowhere. A per-context bag on its own would be close to pointless — everything in it was said in this context, which the transcript already carries — so `user:` is the half that earns the feature.
  - **`temp:` is why the prefixes are parsed at all.** Without it, `temp:draft` would be an ordinary key that outlives the turn under a name saying it does not. For the same reason an unrecognized prefix (`app:`, which ADK has and this does not) is refused rather than read as part of the name.
  - **A `user:` key with no principal is refused**, and the refusal names `[server.auth]`. Filing it against the context instead would be the wrong answer rather than a lenient one — the key says it outlives the conversation, and filed there it would not. Only `jwt` and `oauth2` with an `introspection_url` name a user that survives a token refresh.
  - New `AsyncContextStateStore` port with `NoContextState`, kept apart from `AsyncConversationStore` because the two are configured apart: `mode = "none"` with `remember = true` is a real agent, and so is the reverse. Implemented by `InMemoryTaskStorage` and `SqlxTaskStorage`.
  - Migration `006` gives the bag its own table, **one row per key**. Two turns of one context can run at once — the same reason `context_digests` is append-only — and a read-modify-write over a JSON document loses whichever write lands second without saying so. `006` also drops the unused `contexts.state` column, best effort, since an unused column is not worth failing a startup over.
  - `max_state_chars` (2000) bounds the block and is enforced **where a value is written**, because the block is a system message and `fit` never trims one. A write that would cross it comes back telling the model to `forget` something first.
  - `a2a doctor` reports `remember = true` over in-memory storage, apart from the conversation check: a fact the model was explicitly asked to keep is the one a user notices going missing across the restart the control plane performs on purpose.
  - **BREAKING**: `LlmHandler::with_context_memory` takes the state store as well as the conversation store, and `context::project` takes a `Prompt` struct rather than four positional arguments — three of its fields are optional text about the same conversation, and a summary rendered as remembered state reads plausibly and is wrong.
- **OAuth2 tokens are checked with the authorization server — `introspection_url` (`a2a-rs`, `a2a-agents`)**: `OAuth2Authenticator` matched presented tokens against a list held in the process, which `a2a-agents` never filled — so `[server.auth] type = "oauth2"` produced an agent that rejected every request. It now takes an RFC 7662 introspection endpoint (`OAuth2Authenticator::with_introspection`, `[server.auth] introspection_url`), authenticates to it with the same `client_id`/`client_secret`, and refuses anything the server reports as inactive.
  - The principal is the `sub` from the response, so **a refreshed token is the same caller** — which is what `[handler.llm.context] mode = "context"` needs to decide whose conversation a `contextId` refers to. Previously the id was `oauth2:{access_token}`, and a refresh silently orphaned everything the agent held for that user. A client-credentials token has no end user, so `client_id` is the subject there; a response naming neither is an error rather than a quiet fall back to the token, since falling back would put the credential in the principal id on exactly the server that gave us nothing better.
  - `with_valid_tokens` stays for tests and is ignored once introspection is configured — a static list cannot know about a revocation, which is the thing introspection is for.
  - **BREAKING for configs**: `[server.auth] type = "oauth2"` without an `introspection_url` no longer loads. Such an agent binds its port, serves a card and refuses every request, which is the class of silent-wrong `a2a validate` exists to catch — and it is what every OAuth2 config did until now.
- **ID tokens are verified against the provider's keys (`a2a-rs`)**: `OpenIdConnectAuthenticator` discovered the provider at startup, then ignored everything it learned — it matched the presented ID token against a list held in the process and reported `oidc:{token}`. So it refused every token a real provider issues, and named a credential when it did not. It now verifies the token: signature against the provider's published keys, `iss`, `exp`, and `aud` naming this `client_id`. The principal is the `sub`, so signing in again is the same caller.
  - **`aud` is the check that matters here.** An ID token is issued to one client; accepting one issued to another would let any application the user has signed into speak for them at this agent.
  - **A rotated signing key does not take a restart.** Discovery fetches the key set once, so a token signed with a key issued later names one the agent has never seen. That failure — and only that one — fetches the set again and retries, at most once every `DEFAULT_KEY_REFETCH_INTERVAL` (60s, `with_key_refetch_interval`). The floor is the point: an unverifiable token is also what a flood of junk produces, and that must not become a request to the provider per attempt.
  - `with_valid_tokens` is gone. It existed because there was no verification; there is now, and the authenticator cannot be constructed without a provider to verify against.
  - A context labelled `oauth2` is accepted as well as `openidconnect` — that is what the bearer extractor calls an `Authorization: Bearer` header, and an ID token arrives in one. **A caller presenting an opaque access token still needs `OAuth2Authenticator::with_introspection`**: the same OIDC provider issues both, and only the authorization server can say anything about an opaque token. That is why `[server.auth]` in `a2a-agents` has `oauth2` and no separate `oidc`.
- **Agents can remember the conversation — `[handler.llm.context]` (`a2a-rs`, `a2a-agents`)**: `LlmHandler` started every turn from `[system, user]` and ignored `session_id`, so a "long-running agent" was a stateless function called repeatedly. It can now carry the conversation across turns and keep it inside the model's window. Off by default (`mode = "none"`) — carrying history changes what an existing agent costs and how it answers.
  - **The conversation was already in the database.** `task_history` is append-only, ordered by an autoincrement id, and stores a full `Message` per row; it just could not be read by context. Migration `004` denormalizes `context_id` onto it (a task's context never changes) with an index on `(context_id, id)`, and `005` adds `contexts` and `context_digests`. This mirrors Google ADK, A2A's reference companion, where a `Session` *is* a `contextId` — so `mode = "context"` reads the same rows `tasks/get` does rather than keeping a second transcript that can disagree with it.
  - New `AsyncConversationStore` port — `load` returns the newest digest **and** the messages after its watermark in one call, `compact` appends a digest. Deliberately not split into two ports: a digest written between two separate reads leaves either a gap or duplicated turns in the prompt, and one method makes that boundary something an implementation can actually solve. Implemented by `InMemoryTaskStorage` and `SqlxTaskStorage` over the same state they already keep, plus `NoConversationMemory` so `mode = "none"` is a wired-up choice rather than an absent collaborator.
  - Compaction **appends** a summary with a watermark and deletes nothing. Two turns of one conversation can therefore compact at once: both digests land, the higher watermark wins on load, and the loser is duplicated work instead of a corrupted transcript — which is why no lock is needed across an LLM call.
  - New pure `a2a_agents_common::context` module (`ContextBudget`, `TokenEstimate`/`CharEstimate`, `project`, `fit`, `cap_tool_result`), with no I/O and no protocol types, so the trimming rules — the part with the edge cases — are testable without a database or a model.
  - Trimming gives things up cheapest-first: cap tool results to head+tail, then drop whole tool call/result pairs while keeping the assistant text that concluded from them, then summarize. The system prompt and the message being answered are never touched; a budget too small for those fails naming `max_input_tokens`, because dropping half a question yields a confident answer to something nobody asked.
  - `keep_recent_turns` is honoured by compaction: only what falls before the recent window is folded into a summary, and the digest's watermark is the last message actually summarized. Reading and compacting deliberately use different windows — a load reaches back several of them, because sizing both from one number means the load returns exactly the window compaction may not touch and no summary can ever be written.
  - **A conversation belongs to whoever started it.** Reading conversations back makes a caller-supplied `contextId` decide which conversation you get, so the stores record a `contexts.owner`, claim it on first read, and answer `A2AError::ContextAccessDenied` to anyone else. The owner is the principal the transport authenticated (see the `RequestContext` entry below); on an agent with no `[server.auth]` there is no principal, contexts are unowned, and any caller holding a `contextId` can read one. `jwt` and `oauth2` (with an `introspection_url`) name a *user* and survive a refresh; `bearer` and `api_key` name the credential. `a2a-agents/docs/authentication.md` has the table.
- **`[llm] stream_usage` (`a2a-agents`, `a2a-llm`)**: whether a streaming request asks for `stream_options.include_usage` was decided by string-comparing the base URL against OpenAI's, so the same endpoint written with a trailing slash silently stopped reporting what it cost. The comparison now ignores the trailing slash, and a config can state it outright — which is the answer for a server this crate has no way to recognize, such as a proxy in front of OpenAI or a self-hosted vLLM. Unset, the endpoint still decides.
- **LLM token usage is reported (`a2a-llm`)**: neither provider parsed the `usage` block, so nothing measured what a request cost. `LlmResponse` gains `usage: Option<TokenUsage>` and streaming gains a terminal `LlmStreamEvent::Usage`, parsed from OpenAI-compatible `usage` (including `completion_tokens_details.reasoning_tokens`) and Gemini `usageMetadata`. The handler logs it against what it estimated, which is how the estimator's character ratio gets checked against whatever model the config now points at. Streaming usage is opt-in per endpoint (`OpenAiConfig::stream_usage`, on for OpenRouter and OpenAI's own URL) because local OpenAI-compatible servers vary on `stream_options` and one that rejects unknown parameters fails the whole call.
- **PostgreSQL storage, for real (`a2a-rs`, `a2a-agents`)**: `SqlxTaskStorage` held a `SqlitePool` and `validate_url` refused every other scheme, while the `postgres` and `mysql` features compiled a sqlx driver nothing used and both READMEs plus `docs/SQLx_Storage.md` advertised PostgreSQL. It now runs on either backend, chosen from the URL scheme at runtime: `sqlite::memory:`, `sqlite:tasks.db`, or `postgres://user:pass@host/db`. `[server.storage] type = "sqlx"` in an agent config takes the same URLs, so the control plane can restart an agent onto another host without it forgetting anything, and several instances of one agent can answer behind one address.
  - **One database per agent, not one per fleet**, and `a2a validate --fleet` / `a2a up` now say so: new `FleetConflict::Storage` reports two members pointing at the same URL. Nothing in the schema names the agent, so they would share one namespace for tasks and one for conversations — and a `contextId` reaching both is what delegation produces by itself, so one agent would answer out of the other's transcript. Sharing a *server* is fine. What would make sharing a database safe is the multi-tenancy work in `TODO.md`.
  - **One set of queries, two schemas.** The store executes through sqlx's `Any` driver, so the ~40 queries are written once; what differs is in one internal `Dialect` type — parameter placeholders (`?` → `$1`), the two upserts, and the timestamp comparison. The schema is the part that cannot be shared, and it is written twice under `migrations/sqlite/` and `migrations/postgres/` (identity columns, timestamp defaults, and the `updated_at` triggers have no common spelling). A second copy of the *store* is what would let the backends drift, which is what the old `_postgres.sql` files had already done.
  - JSON payloads are `TEXT` on PostgreSQL rather than `JSONB`, and no query selects a timestamp column. The runtime-dispatched driver decodes text, integers, floats, booleans and bytes, and converts a row whole — so a `jsonb` or `timestamptz` column in a result set fails the read. Nothing queries into the JSON, so this costs operators nothing.
  - **Agents starting together do not race.** A shared database is the reason to run PostgreSQL, so a fleet coming up at once is the normal case — and concurrent `CREATE TABLE IF NOT EXISTS` on related tables deadlocks rather than no-opping (seen, not theorized: nine concurrent test processes). Migrations run on a one-connection pool of their own, holding `pg_advisory_lock` for the duration, with a retry on the duplicate-object and deadlock SQLSTATEs behind it.
  - **BREAKING**: the `mysql` feature is gone. A `mysql:` URL is still recognized so the error can name it; there is no MySQL schema and never was.
  - `sqlite::memory:` keeps meaning one database per store. sqlx invents a fresh name for an anonymous in-memory database *per URL parse*, and the runtime-dispatched driver parses per connection — so without pinning a name, a ten-connection pool would be ten empty databases.

- **SQLite connections are told to enforce foreign keys (`a2a-rs`)**: `foreign_keys` is a per-connection pragma that SQLite defaults to *off*, so every `ON DELETE CASCADE` in `migrations/sqlite/` is decoration unless each connection turns it on. It has in fact been on all along — sqlx's `SqliteConnectOptions` defaults it true — but nothing here said so, leaving a schema that cannot work without it resting on a dependency's default. `SqlxTaskStorage` now sets it in `after_connect`, on both the main and the migration pool, which is the only place it can be said: the `Any` driver parses URLs itself and rejects SQLite's own parameters. No behaviour changes; three tests pin it, including one that deletes a task and checks its history went with it. PostgreSQL is untouched — it enforces its constraints without being asked.

- **Retention: `RetentionPolicy` and the `AsyncRetention` port (`a2a-rs`)**: the conversation log became durable in 0.5 and nothing ever deleted from it, so a long-lived agent grew without bound — `InMemoryTaskStorage` most obviously, which never evicted a task, a conversation, a digest or a state key. `AsyncRetention::sweep(&policy, now)` deletes what the policy has expired and reports a `Swept` count per table; `InMemoryTaskStorage` and `SqlxTaskStorage` both implement it, tested against one shared body so the two cannot mean different things by "idle".
  - Two knobs, both off by default (`RetentionPolicy::keep_everything`). `delete_contexts_idle_for` sweeps a context whole — its tasks, conversation, digests, push configs and `context:`-scoped state. `delete_user_state_idle_for` is separate because a `user:` bucket belongs to a principal rather than to a context: it is readable from a context that principal has not opened yet, so no context going idle says anything about whether it is stale. It expires a principal's bag whole, since a bag that remembers somebody's city and not their name reads to a model as fact rather than as absence.
  - Off by default because `tasks/get` with `history_length` is a protocol feature: a swept context turns a call the client is entitled to make into a `TaskNotFound`.
  - A context holding an unfinished task — `submitted`, `working`, or a state this build cannot read — is never swept, however long it has been quiet. `input-required` and `auth-required` do not hold it back: they wait on a caller who, past the retention window, is not coming back.
  - No timer and no background task. A sweep deletes data an operator cannot get back, so *when* it runs belongs at the composition edge next to the policy. `now` is a parameter for the same reason it is testable: a caller that cannot name the cutoff cannot test a retention window without waiting one out.
  - A swept task takes its push-notification config with it in both adapters — a SQL `DELETE` against one, `PushNotificationRegistry::unregister` against the other — so a webhook URL cannot outlive the task it was registered against.
  - The SQL sweep names every table explicitly rather than leaning on the schema's `ON DELETE CASCADE`. The cascades do fire on both backends, but only some of what a sweep deletes is reachable through them — `context_state` has no foreign key at all, since half its rows are keyed by principal rather than by context — and the per-table counts in `Swept` need the statements anyway.
  - The sweep runs against a real PostgreSQL server in CI, not only against SQLite: the `UNION ALL` over five tables that finds a context's last write, the `EXCEPT` that holds back a context with a running task, and the `$1::timestamptz` the cutoff binds through all have a separate PostgreSQL spelling, and unit tests over the query strings can only check placeholders and state names. `retention_test.rs` gives each case its own database — a sweep is global, so cases sharing a server would delete each other's contexts — and skips the whole suite when `A2A_TEST_POSTGRES_URL` names no server. One case was missing on every backend: a compacted context, which is the only thing that writes a `context_digests` row.

- **`HttpServer::serve_on` takes a listener the caller already bound (`a2a-rs`)**: `start` binds the configured address itself, so a caller that asked for port 0 had no way to learn which port it got, and no caller had a way to tell when the socket began accepting. `serve_on` takes a bound `TcpListener` instead: `local_addr()` reports the real address, and the kernel queues connections from the moment of the bind, so a client may connect before the serve future is first polled. `start` is now bind-then-`serve_on` and behaves as before. A supervisor that hands out port 0 and reports back the port the agent actually listens on needs this; so does any test that would otherwise sleep and hope.

- **Every crate ships its license text**: all seven declared `license = "MIT"` and none carried a LICENSE file.
- **`examples/jsonrpc_server` supports streaming (`a2a-rs`)**: it is the server this repo points other SDKs' clients at, and it was built with no streaming backend — `SendStreamingMessage` and `SubscribeToTask` answered `UnsupportedOperation`, and its card did not claim the capability either. It now wires `InMemoryStreamingHandler` and advertises `streaming`.
- **A turn asks who owns a context once, not once per port call (`a2a-rs`)**: reading the claim before writing it (below) got a turn down to one statement per call, and a turn makes several — the conversation read, the state-bag read, and one more for every key it remembers. `SqlxTaskStorage` now keeps the settled answer for a few seconds (`SqlxStorageBuilder::claim_cache`, `DEFAULT_CLAIM_CACHE_TTL`), so a turn with `mode = "context"` and two `remember` calls asks once instead of four times.
  - **A cache of an authorization input needs an argument, and this is it: the value cached cannot change.** `contexts.owner` is written once, by the claim, and never reassigned — `Open` stays open and `Owner(x)` stays `x`. A hit is not a second opinion about who owns a context; it is the same answer read less often. What can happen to the row is *deletion*, by a retention sweep, after which a different principal may claim the id afresh.
  - Three things bound that. Only settled answers go in, so the absent row — the one case a caller has to act on by writing — is never cached and the claiming path is untouched: it still reads before it writes and still reads back rather than trusting `rows_affected`. The store evicts what its own sweep deletes, after the commit. And the TTL bounds a sweep run by *another* replica, whose window needs that replica to sweep a context idle for days, a different principal to re-claim the same id, and this replica to serve a request against it, all within a few seconds. `claim_cache(None)` opts out where that is not a trade worth making.
  - The entry holds the **claim**, never the verdict, so `ContextClaim::verdict` still runs per request and one cached row cannot admit the wrong caller. Bounded at 1024 contexts, cleared whole when it fills — a miss costs one `SELECT`, which is not worth an LRU or the dependency one would arrive with. Nothing changes for the in-memory store, whose check is a mutex lookup rather than a statement.

- **Checking who owns a context costs one statement, not two (`a2a-rs`)**: `SqlxTaskStorage` claimed the context and then read its owner back — an insert and a select — on every conversation read and every state-bag read. An agent with `mode = "context"` *and* `remember = true` therefore made four statements about ownership before the model was called, and every `remember` made two more. Ownership is first-write and is never reassigned, so an existing row is the whole answer: the read comes first and only its absence writes. Every turn after the one that opens a context now asks once. The in-memory store already had this as a single `claim_or_check_context`; the two adapters now have the same shape and the same name.
  - The claiming path still reads back rather than trusting `rows_affected` to say whether the insert was ours. Two callers can open one context in the same instant, and a driver that counted an ignored insert as a row would let the loser into a conversation it does not own — `contexts.owner` is an authorization boundary, so the extra statement buys not resting it on how each backend reports a no-op.

### Removed

- **BREAKING — `GEMINI_DEFAULT_MODEL`, and the idea of a default Gemini model (`a2a-llm`)**: the constant was `gemini-1.5-pro`. As of 2026-08-25 Google does not list that model on its current models page, and does not list it on the deprecation schedule either — so nothing has been announced about it in either direction, and every config naming `provider = "gemini"` without a `model` had been running on it regardless. `model` is now required for Gemini: `GeminiConfig::from_lookup` requires `GEMINI_MODEL` the way it already required `GEMINI_API_KEY`, and `build_from_settings` refuses a `[llm]` block that supplies neither a `model` nor that variable.

  - korps' half is a config decision this cannot make for it: a `[llm]` block with `provider = "gemini"` and no `model` is now a startup error, so `korps validate` should say so before a run does. See korps' `TODO.md` §2.

- **The legacy v0.x send-params types (`a2a-rs`)**: `MessageSendParams`, `MessageSendConfiguration` and `TaskSendParams` were the hand-written JSON-RPC v0.x request shapes. Neither transport read them — the v1.0 path decodes the generated proto request types — and nothing in this workspace or in korps named them. `MessageSendConfiguration.blocking` is the case that made the family worth deleting rather than documenting: it is the v0.x spelling of `return_immediately`, which is now modelled as `SendCompletion` and wired through both transports, so keeping it left two spellings of one thing with only one of them connected to anything. **BREAKING**: the three types are gone from `a2a_rs::domain` and from the crate root. `TaskIdParams`, `TaskQueryParams`, `ListTasksParams` and `ListTasksResult` stay — the ports read those.

### Fixed

- **A Gemini candidate cut before any content lost its reason (`a2a-llm`)**: a reasoning model that spent the whole output budget thinking answers `finishReason: "MAX_TOKENS"` with no `content`, and `chat_completion` failed it as `ProviderError("No content in response")` — reading the content before the reason, so the one empty answer a caller can act on (raise the output cap) raised the same opaque fault as a truly empty one. A candidate with a reason and no content is now an empty `LlmResponse` with `finish` set, the shape the OpenAI path already returns for a choice with no content; a candidate with neither is still the provider error. Deliberately left out of the 0.4.0 finish-reason work; `tests/wire_test.rs` pins both over a socket.

- **`Finish` arrived twice from OpenRouter (`a2a-llm`)**: it puts `finish_reason: "stop"` on the last content chunk *and* on the usage-only chunk after it, and the stream forwarded both as `LlmStreamEvent::Finish(Stop)`. Seen from korps' live runs on 2026-09-02 — korps records it as a fact and did not break, but a consumer that counted finishes, or took the first as the end of the stream, would have. The stream now emits a reason once; a *different* reason would still be news and still comes through. `Finish`'s doc says the rest: it is a fact, not a terminator. Checked against the unfixed stream: two `Stop`s.

- **`a2acli send` could not continue a conversation (`a2acli`)**: the flag existed under the wrong name — `--session-id` was already the message's `context_id` on the wire, which nothing said, so continuing from the CLI looked like it meant reusing a task id: a different thing on the wire, and a settled task is not a conversation handle. It is `--context-id` now, matching `list`, and a finished task's next-step hint points at its context rather than falling silent. Found driving the 2026-09-01 korps wake-up session by hand.

- **A refused subscription reached the ConnectRPC client as an empty stream (`a2a-rs`, #71)**: a server that refused a `SubscribeToTask` outright — the adapter's default `NoopStreamingHandler`, or `TaskService::subscribe` on a task that had already settled — returned `Ok(stream)` from `HttpClient::subscribe_to_task`, and the first `next()` was `None`. The refusal was indistinguishable from a task that settled with nothing to say. A Connect streaming call answers HTTP 200 before the handler runs, so a pre-stream error goes in the END_STREAM envelope, and the client library parks it in `ServerStream::error()` behind an ordinary `Ok(None)`; the `unfold` never read it. It does now, and yields the refusal as the first (and only) item, so "the peer said no" and "the peer said nothing" are different again.
  - Found from downstream: korps' `[features] streaming = false` refuses at the transport with `UnsupportedOperation`, and its wire test could only see the refusal through the JSON-RPC client.
  - `tests/connectrpc_error_test.rs` observes both pre-stream refusals over a real socket, and that the stream ends after saying so rather than repeating it. All three checked against the unfixed code: each reports the empty stream.

- **ConnectRPC lost the A2A error code on the way through (`a2a-rs`, #72)**: `PushNotificationNotSupported` (`-32003`) fell into the server's catch-all and went out as `Internal`, which the client read back as `-32603` — a spec-defined refusal labelled as a server fault, inviting a retry that would be refused again. `UnsupportedOperation` (`-32004`) went out as `Unimplemented`, the same code as `MethodNotFound`, and came back as whichever the client's table preferred. The general shape was two tables, one per direction, each with a catch-all: any variant missing from either decoded as something else. Connect has sixteen codes and no bijection onto A2A's exists, so the A2A code no longer round-trips through the Connect code at all. The server attaches the JSON-RPC error object — code, message, typed details — as a Connect error detail (`type: "a2a_rs.JsonRpcError"`), and the client reads it back through the JSON-RPC table; the Connect code stays as the nearest category, for a client that is not ours. New `connect_wire` module holds both directions, the way `jsonrpc_wire` does for that binding.
  - **One table for both bindings.** `jsonrpc_wire::error_code` re-exports the domain's constants instead of copying them, `a2a_error_code` is exhaustive over `A2AError` (so a new variant is a compile error rather than a `-32603`), and `jsonrpc_to_a2a` now rebuilds every spec code as its variant, not five of them. `ContextAccessDenied` carries its `context_id` as `ErrorInfo` metadata so the typed variant survives.
  - **Behaviour change on the JSON-RPC client too**, in the same direction: an error that used to arrive as `A2AError::JsonRpc { code: -32002, .. }` arrives as `A2AError::TaskNotCancelable(_)` now, and so on for `-32003`, `-32005`, `-32006`, `-32100`, `-32102`, `-32603` and the two request-shape codes. A caller that matched on the number will want the variant; one that matched `JsonRpc { .. }` as a catch-all still gets it for codes this crate does not know. On the JSON-RPC *server* side, `ContextAccessDenied` and `DatabaseError` were going out as `-32603` from the wire table's catch-all while the domain's own constants said `-32102` and `-32100`; they send the domain's number now.
  - Found from downstream: korps refuses push configs with `PushNotificationNotSupported` when `[features] push_notifications = false`, and its wire test could only assert on the message substring.

- **Three of the five authenticators could not be reached through `with_auth` (`a2a-rs`)**: the middleware extracted credentials with a hard-coded `BearerTokenExtractor`, while every `Authenticator` refuses a context labelled with a scheme other than its own. So an `ApiKeyAuthenticator`, an `OAuth2Authenticator` and an `OpenIdConnectAuthenticator` each rejected the very credential they had been configured to accept: the API key stayed in `X-API-Key` unread, the access token was labelled `bearer` where `oauth2` was required, and the server answered 401 to every request — valid ones included. Only `bearer` and JWT worked, because those are the two that expect what the bearer extractor produces. `AuthState::new` now derives its extractor from `authenticator.security_scheme()`.
  - **No API change.** `AuthState` lives in a private module — only `with_auth` is exported — and the trait method the fix reads has always been required. The `with_extractors` constructor that sat beside it under `#[allow(dead_code)]` is the tell: the seam existed and nothing could reach it.
  - **What the card advertises is what the server reads.** The scheme is the same value that goes on the agent card, so a client that reads the card and sends what it says now gets in. Those were two descriptions of one fact with only one of them exercised.
  - **Headers only, and stated rather than implied**: an API key configured with `location = "query"` or `"cookie"` extracts nothing and the request is refused. Deliberate on the query side — a credential in a URL is a credential in every access log and referrer — and `AuthState::with_extractors` is there for a caller who needs another.
  - `tests/auth_scheme_extraction_test.rs` covers each scheme as a pair — the right credential is accepted *and* a plausible wrong one is refused — because either assertion alone passes against a server that refuses everybody, which is exactly what this was. Both "accepted" tests were checked against the old code and fail there.
  - Found from downstream: korps refused to serve `[server.auth] type = "apikey"` at all rather than serve it open, and reading why turned up that `oauth2` had the same defect.

- **A task's status message was never stored by `SqlxTaskStorage` (`a2a-rs`)**: a completed task read back from SQLite or PostgreSQL had the right state and no `status.message` — so the agent's reply, which is what a client reads off a finished task, was only in `history`. `InMemoryTaskStorage` carried it, as the domain's own `Task::update_status` does, so the same agent answered differently depending on one key in its config.
  - One missing column in three statements. `update_status`, `update_status_checked` and `cancel` each wrote `status_state` and left `status_message` holding whatever `create` inserted — normally `NULL`. The column, the read in `row_to_task` and the `TASK_COLUMNS` list were all correct and always had been; nothing wrote to it after insert. `cancel` had the sharper version: it builds a cancellation message, put it in history, and left the canceled task unable to say why.
  - **A status carrying no message now clears the previous one**, rather than skipping the column and leaving it. The domain replaces the whole `TaskStatus`, and a message left behind is attributed to a state it was never about — a stale answer reads worse than an absent one.
  - **New `tests/storage_parity_test.rs`**, which is the part that keeps it fixed: the assertions live once and the backend is the parameter. Each adapter having its own file asserting what that adapter does is precisely what let two implementations of one port drift while both suites stayed green. Checked against the unfixed code — in-memory passes, sqlx fails on the completed-task assertion — so it tests the difference rather than restating the new behaviour.
  - The `TaskState` → column-string match had five copies, against a sixth that reads it back; a state written under a spelling the reader does not know comes back as `Unknown`. One `state_str` now.
  - Found from downstream: one korps agent pointed at both backends, answering the same question two ways.

- **llama.cpp's context overflow was not recognized as one (`a2a-llm`)**: `CONTEXT_LENGTH_MARKERS` carried a `// llama.cpp, vLLM` comment over `"too many tokens"` and `"exceeds the maximum"`, and llama.cpp says neither. b10524 answers an over-long request with `{"error":{"code":400,"message":"request (40089 tokens) exceeds the available context size (32768 tokens), try increasing it","type":"exceed_context_size_error",…}}` — "context **size**", not "context length"; "exceeds the **available**", not "exceeds the maximum". The classification test carries the b10524 body verbatim.
  - Found downstream, by pointing a `korps` agent at a local llama.cpp server and overflowing its window on purpose. Worth noting as the shape these misses have: the marker list is only ever wrong about a server nobody has actually run it against, and it names the servers it was *written for*, not the ones it was tested against.

This crate was the only 0.7 left in the workspace, and because `create_sse_stream` returns an `Sse`, its version reached every dependent that wanted the helper — korps carried a dev-dependency alias for exactly this. Routes in the docs and the `sse_streaming` example take 0.8's `{task_id}` path syntax.
  - `async-stream` was declared, gated behind the same feature, and imported nowhere in the crate. Dropped.
  - **A CI job now builds the workspace with `--no-default-features`**, which is what would have caught this: every other job builds with features *on*, so a feature was only ever proven in one direction. The general answer is `--feature-powerset`; this is its cheap half, covering the mistake that actually happened.

- **`SendMessage` rejected a message with no task id ([#51], `a2a-rs`)**: `a2a.proto` marks a client message's `task_id` and `context_id` optional — a client with nothing to continue sends neither and the server names the task. Both transports instead read `message.task_id` straight through to `TaskId::from_str`, which rejects the empty string proto3 delivers for an omitted field, so every such request came back `-32602 task_id cannot be empty`. A conformant client could not open a conversation at all.
  - `TaskService` now resolves both ids before the handler runs, and the whole rule lives in that one place: no task id means a generated one; a task id we hold means that task's context wins; a context id contradicting the stored task is refused rather than silently re-homing the message, since the spec requires the two to match. The `AsyncMessageHandler` port is unchanged — a handler still receives a resolved id.
  - The resolved ids are written back onto the message before it lands in history, so a client that sent none reads them off `history[i]` instead of `""`.
  - Removes the `"default"` context fallback in `ResponderMessageHandler`, which filed every context-less task on a server under one shared context id.
  - **BREAKING**: `TaskService::send_message` and `send_streaming_message` take the `Message` by value and no longer take a separate `task_id` — both adapters were passing `message.task_id.clone()` into it.
- **A client had to invent a task id (`a2a-rs`, `a2acli`, `a2a-mcp`, `a2a-web-client`)**: the other half of [#51]. `Transport::send_task_message` required a `&str`, so `a2acli` and both bridges generated a client-side UUID for a task the server was about to name — and a server that assigned a different id would have left the caller polling one that does not exist.
  - **BREAKING**: it takes `Option<&str>` now. `None` starts a task the server names; read the id off the returned task. `Some(id)` continues one the caller holds. `RetryingTransport` still forwards sends rather than retrying them, which matters more with `None`: a retry would create a second task instead of reattempting the first.
- **Push notification configs did not survive a restart (`a2a-rs`)**: migration 002 began with `DROP TABLE IF EXISTS push_notification_configs` before recreating it in the v0.3 shape, and the base migrations re-run on every `SqlxTaskStorage::new`. So every process start silently destroyed every webhook the agent had been told to call — persistent storage that dropped exactly the thing an operator configures once and expects to stay. The drop now happens only when the table is still the pre-v0.3 one, decided by probing for its `webhook_url` column, and a test reopens a database to prove the config is still there.
- **A wrapped `reqwest::Error` dropped its cause (`a2a-agents-common`, `a2a-rs`)**: `reqwest::Error`'s `Display` deliberately omits its source chain, so `Network error: error sending request for url (…)` was the whole message for a DNS failure, a refused connection, and an untrusted certificate alike — which is what made a TLS-intercepting proxy indistinguishable from the network being down and cost a full investigation. Every site that flattens one into a string now walks `Error::source()` into the message: both LLM providers (including the SSE stream's wrapper), `HttpClientError`, and the new OAuth2 introspection call.
- **Two server tests raced the port they bound (`a2a-rs`)**: `authenticated_principal_test`'s ConnectRPC case bound a hard-coded `127.0.0.1:8199` and slept a flat 200ms waiting for the server. It failed once under `cargo test --workspace --all-features` and passed on its own and on a re-run — the shape of both candidate causes, another test binary holding the port and the sleep being short under load. Both are gone rather than one: the test binds `127.0.0.1:0` and hands the listener to `serve_on`, so the port is whatever was free and the socket accepts before the client connects. `agent_card_transport_test` had the same shape — a bind-and-release `free_port()` plus up to five seconds of polling for the card — and is race-free the same way. The ConnectRPC case went from 200ms to 34ms.
- **The official client could not read our agent card at all (`a2a-rs`)**: `SimpleAgentInfo::add_skill` built every skill with empty tags. `AgentSkill.tags` is REQUIRED in `a2a.proto`, and ProtoJSON omits an empty repeated field — so the served card carried no `tags` key and the official `a2aproject/a2acli` refused to decode it. It fetches the card before every call, so `card`, `send`, `get-task`, `list-tasks`, `cancel-task` and `stream` all failed identically with "error decoding response body", on both bindings. **BREAKING**: `add_skill` and `add_comprehensive_skill` take `tags: Vec<String>` (no longer defaulted, no longer `Option`), because a skill with no tags cannot be put on the wire as one. A new `agent_card_required_fields_test` asserts a plainly-built card serializes with every REQUIRED field present, at card, skill and interface level — the next field that silently defaults to empty is caught here rather than by somebody else's client.
- **The canonical task paths were unroutable, and failed two different ways (`a2a-rs`)**: the spec puts the verb on the same segment as the path parameter (`POST /tasks/{id=*}:cancel`, `GET /tasks/{id=*}:subscribe`), which axum's matchit cannot register — `{id}` already claims the whole segment. `rest_router` served only the slash aliases (`/tasks/{id}/cancel`) on the belief that official clients accept those; they do not send them. `POST /tasks/{id}:cancel` matched the `GET`-only `/tasks/{id}` route and came back a bare `405`, and `GET /tasks/{id}:subscribe` matched it outright and answered with the *task* as JSON to a client waiting on an event stream. The `/tasks/{id}` handlers now split a known verb off the captured id (exact `:cancel` / `:subscribe` suffix only, so `urn:uuid:7` is still a task id) and dispatch accordingly. The aliases stay.
- **A streaming response never ended for an agent that answered immediately (`a2a-rs`)**: `send_streaming_message` closed its stream on the event that settles the task — but a handler that finishes inside `process_message` returns a `COMPLETED` task having broadcast nothing, so no such event could ever arrive. The subscription is a broadcast receiver, which parks rather than ending, and the SSE response stayed open until the client gave up: the official `a2acli` hung until its timeout on every `stream` call against the echo example. An already-terminal task now drains whatever is queued and ends (`ready_queued`), mirroring the short-circuit `subscribe` has always had. Queued events are still delivered rather than dropped, since an artifact chunk a handler streamed without attaching to the task exists nowhere else.
- **BREAKING — `SubscribeToTask` on a finished task is refused (`a2a-rs`, `a2acli`)**: `a2a.proto:75` specifies `UnsupportedOperationError` when the task is already terminal; `TaskService::subscribe` returned the task's snapshot and an empty stream instead. On the wire that is a subscription which opens and closes having said nothing — indistinguishable from an agent that has yet to speak — and a caller that only reads events, which is the point of subscribing, saw nothing at all. It now returns `A2AError::UnsupportedOperation` naming the state. Resumption is unaffected: a request carrying `Last-Event-ID` still opens, because a task finishing during a disconnect is precisely when the replay buffer is what the client reconnected for. `a2acli`'s wait falls through to polling when the subscription is refused, and `poll_until_settled` now reads before it sleeps so that path costs nothing.
- **A JSON-RPC error on the streaming path arrived as an empty stream (`a2a-rs`, `a2acli`)**: `JsonRpcClient::subscribe_to_task` checked the HTTP status and nothing else. An error answering a streaming call is HTTP 200 with a JSON body — the transport succeeded, the call did not — so the SSE reader found no `data:` frames and handed back a stream that ended immediately. `a2acli stream` then printed nothing and exited 0. Found pointing our client at the upstream `a2aproject` agent, which answers `SubscribeToTask` on a finished task with `-32001 task not found`: the server said exactly what was wrong and the client discarded it. The client now diverts on the response's content type — anything that is not `text/event-stream` is decoded as a JSON-RPC envelope and its error mapped through `jsonrpc_to_a2a`. A response with no content type at all is still read as a stream, since consuming a body to inspect it would hang on a stream that has nothing to say yet.

### Fixed

- **Task history could come back in the wrong order (`a2a-rs`)**: `SqlxTaskStorage::load_task_history` ordered by `timestamp`, whose default is `datetime('now')` — second resolution in SQLite — so rows written in the same second had no defined relative order. Nobody noticed while history was short and read for display; rebuilding a conversation from it puts turns in the wrong order at random. It now orders by `id`, the autoincrement insertion order, which is also what the conversation log means by sequence. The same query filtered out `NULL` messages *after* applying `LIMIT`, so `history_length = 5` returned fewer than five whenever a status transition carried no message; the filter moved into the query.
- **Every outbound HTTPS call failed behind a TLS-intercepting proxy (workspace)**: `reqwest` was built with `rustls-tls` alone, whose trust anchors are the compiled-in webpki roots. rustls does not read `SSL_CERT_FILE`, so a CA installed on the machine — a corporate MITM gateway, or a [Docker Sandbox](https://docs.docker.com/ai/sandboxes/) configured to re-sign egress — could not be trusted from outside the binary at all. Every LLM call, remote-peer delegation and MCP-over-HTTP request died as `Network error: error sending request for url (…)`, with the certificate error dropped from the message and `curl` in the same shell working fine. The workspace dependency now also enables `rustls-tls-native-roots`; reqwest's two root stores are additive, so the built-in roots remain the floor for a machine with no trust store and the OS store adds whatever the operator installed. The TLS decision now lives once in the workspace `Cargo.toml` rather than in three crates.

If the budget runs out the task is printed as it stands, followed by the `stream`/`get` commands that follow it.
- **`a2acli send` waits on the event stream, not a poll loop (`a2acli`)**: the wait now prefers `subscribe_to_task` and keeps polling only as the fallback. Against a conformant server this path does not run at all (the task comes back settled); what it is *for* is a peer that ignores `return_immediately`, and there a subscription wakes on the agent's actual progress rather than on a 250ms timer, and ends by itself the moment the task settles. Polling remains for a peer with no streaming backend, or one whose stream drops before the task finishes — the wait re-reads the task after the stream ends and resumes polling if it is still unsettled, so neither mechanism failing can turn a finished task into a timeout. The "waiting up to Ns…" notice is now on a timer of its own, so a fast agent still prints nothing.
- **BREAKING — `--auth` / `--timeout` work in `auto` transport mode (`a2acli`, `a2a-rs`)**: transport negotiation built unauthenticated, default-timeout clients, so credentials applied only when a transport was pinned with `--transport` — and the CLI could do no better than log a warning that it was ignoring them. The **card fetch carries the credentials too** — an agent that guards its RPC endpoints usually guards its card, and a 401 there sank the whole negotiation before any of it could be authenticated. ### Fixed

- **An LLM agent that gave up reported success (`a2a-agents`)**: `LlmHandler` ended a tool-call budget overrun with `Ok("I could not converge on an answer within the tool-call budget.")` — a **completed** task whose text said it had failed. Every caller that branches on state read that as success: `a2acli` exits `2` on `failed` and so exited `0`, and agent-to-agent delegation relayed the apology onward as if it were an answer. It now settles **failed**, naming `max_tool_rounds` as the knob that changes it, and keeps whatever the model said on the way instead of replacing it — a failed task's most useful content is the partial work. `failed` rather than `input-required` because the agent asked the caller no question: prompting for input would restart the same run against the same budget. This and the empty completion below were the same missing outcome — a run that finished without breaking *and* without delivering — so `run_with_llm` now returns `Answer::{Given, GaveUp}` and the two share one representation rather than two patches.
- **BREAKING — a task the agent failed exited `0` (`a2acli`)**: the request succeeding and the *work* succeeding are different facts, and the CLI reported only the first — so `a2acli send "ship it" && ./deploy.sh` deployed on a failed task. `send` and `get` now exit **`2`** when the task's state is `failed` or `rejected`, distinct from `1` (the command itself failing) because a timeout is worth retrying and a refusal is not, and one exit code cannot ask for both. Only the agent's own verdicts count: a task still working is not a failure (the caller was told how to follow it), and `cancel` still exits `0` on a canceled task — that is the command working. The task is still printed to stdout in full; the reason goes to stderr.
- **The CLI fell silent exactly when the agent asked a question (`a2acli`)**: `input-required` and `auth-required` are *settled* states, so the "still working, follow it with…" hint did not fire and nothing replaced it — the agent had handed the conversation back and the output read like it had given up. `send` and `get` now print the command that answers on the same task (`send --task-id <id>`), which is the one thing that continues the exchange and the one thing the previous hints never mentioned.
- **A bearer token could be logged in full (`a2a-rs`)**: `ClientConfig` derived `Debug`, so a single `tracing::debug!(?config)` wrote the credential to the log — and this type is precisely what a caller reaches for when tracing *why* a connection did not authenticate, making the most likely line to be written the one that leaks. `Debug` is now hand-written and prints `<redacted>` when a token is set (and `None` when it is not, so the rendering still distinguishes the two cases).
- **A valid-looking URL panicked instead of erroring (`a2a-rs`, `a2acli`)**: `HttpClient::new` ends in `.expect("Invalid base URL")`, while `auto_connect` validated with `reqwest::Url::parse` — which is *more* permissive than the `http::Uri` the ConnectRPC client needs. `reqwest::Url` accepts an IDN host like `http://münchen.de` and normalizes it to punycode; `http::Uri` rejects the raw bytes. The original string was then handed to `HttpClient::new`, so `a2acli --url http://münchen.de send hi` aborted on a URL the same function had just declared valid one line earlier. Worse, the panic sat on the *fallback* path, which is where a questionable URL is most likely to end up in the first place. New `HttpClient::try_new` / `try_with_auth` return `Result`; negotiation, the direct-client fallback, and `a2acli --transport connectrpc` all use them, so a URL the transport cannot represent is now an `InvalidParams` error naming it. `new` / `with_auth` remain as the panicking convenience for a hardcoded literal, now documented as such. The `ConnectRpcTransportFactory` also drops its own duplicate pre-validation — the knowledge that this URL has to be an `http::Uri` now lives in one place.
- **BREAKING — `SendMessage` ignored `return_immediately`, and defaulted to the opposite of the spec (`a2a-rs`)**: the field existed on the generated type and was read nowhere, so the server always behaved as if it were `true` — it acknowledged the message and returned `WORKING`. The proto3 default is `false`, and `false` obliges the server to wait until the task reaches a terminal or interrupted state before returning (`spec/a2a.proto:155`). A conformant client that sends *no configuration at all* — what the official SDKs do — was therefore promised a settled task and handed an unsettled one, which would have made us look like the broken party in the first interop run. The response is now held until the task settles, driven by the streaming handler rather than a poll loop: it already broadcasts every transition, so a subscriber *is* the wait. Bounded by `TaskService::with_send_wait` (25s, deliberately *under* the 30s per-request timeout that `JsonRpcClient`, `HttpClient` and `a2acli` all default to — at equal values the two race and a slow agent surfaces as a transport error rather than the unsettled task the bound exists to return); on expiry the *unsettled* task is returned rather than an error, since `WORKING` is true and leaves the caller a task id to follow. A server with no streaming backend cannot observe transitions and degrades to returning what it has rather than failing the send. Breaking: `TaskService::send_message` now takes a `SendOptions` (push config + history limit + `SendCompletion`) in place of two positional `Option`s, and `SendCompletion::WhenSettled` is its `Default` — the wire's polarity is inverted relative to the name, so the enum spells out which branch is which. Streaming calls deliberately ignore `completion`: there, the stream is the wait.
- **BREAKING — clients could not ask for `return_immediately` (`a2a-rs`, `a2a-agents`, `a2acli`)**: making the server block exposed that the client `Transport` port had no way to opt out, which broke two callers that run their own follow-up. `A2aAgentToolSource` (agent-as-tool delegation) polls with its own deadline, and stacking the peer's 25s wait underneath it silently promoted the longer of the two — a 400ms delegation deadline sat behind a 25s server wait, and its test went from 0.5s to 25.5s. `a2acli send --no-wait` had the same shape: it skipped *client-side* polling while the server blocked anyway, so the flag stopped meaning what it says. `Transport::send_task_message` now takes a `SendCompletion`, and `SendCompletion` moved to `domain` (the client port is feature-gate-free and cannot depend on the `server`-gated application layer — and both directions need it). Delegation and `--no-wait` pass `WhenCreated`; the MCP bridge passes `WhenSettled`, since an MCP tool call is request/response with no poll loop of its own. `a2acli`'s poll loop stays as the fallback for servers that ignore the flag.
- **A subscription never ended, on any transport (`a2a-rs`)**: `subscribe`/`message/stream` kept the connection open after the task reached `COMPLETED` or `FAILED`, so `a2acli stream` had to be capped with an external `timeout` and any conformant client read until it gave up. The underlying stream is a broadcast receiver that ends only when the *sender* closes, which never happens — so the end of a stream was derived from nothing. A2A v1.0 removed the `final` flag from `TaskStatusUpdateEvent` (v0.x had one), so the task state is the only thing left to derive it from. The stream now ends after delivering the event that settles the task, via `UpdateEvent::settles_task`. Three things this turned on that are easy to get wrong: it lives in `TaskService`, not in each transport adapter, because both ConnectRPC and JSON-RPC take their stream from there and a check that runs in one entry point and not the other is not a check; *interrupted* states (`INPUT_REQUIRED`, `AUTH_REQUIRED`) settle a stream too, since otherwise the client waits on the agent while the agent waits on the client; and a final artifact chunk does **not**, because `last_chunk` ends an artifact rather than a task and a `WORKING` task may emit several. Subscribing to an already-terminal task short-circuits to an empty stream — but only when no `Last-Event-ID` was given, since resuming on a task that has since finished is exactly when the replay buffer is what the client reconnected for. Replaces the unused `UpdateEvent::is_final`, whose name conflated those last two cases.
- **A queued task could not be canceled (`a2a-rs`)**: both storage adapters accepted `Working` and nothing else, so `cancel` refused a `Submitted` task — work that had not started, which is the clearest thing a client would ever want to stop — and refused `InputRequired` / `AuthRequired`, where cancelling is precisely how a client says "never mind" rather than being obliged to answer. The rule is now "anything that has not finished", expressed once as `TaskState::is_cancelable` (`!is_terminal`) in the domain and consulted by both adapters instead of each carrying its own copy. An unrecognized state counts as cancelable: a peer on a newer protocol may have states this build does not know, and refusing there strands a task no client can be rid of. A test asserts every state is classified exactly once, so one added to the proto cannot slip through unclassified.
- **BREAKING — `EchoResponder` left every task `Working` forever (`a2a-rs`)**: it attached its reply and then reported that the agent was still thinking, so `examples/jsonrpc_server` completed no task it was ever sent. That is a wire-level lie — any conformant A2A client that waits for a terminal state waits forever, which would have been the first thing an interop run against the official `a2aproject/a2acli` hit. An echo has fully processed the message the moment it has the reply, so `Completed` is the only honest state; agents that genuinely acknowledge-now-finish-later implement `AsyncMessageHandler` directly, as the reimbursement agent does. Downstream: a task from the reference echo is now terminal, so it can no longer be canceled (correctly — `TASK_NOT_CANCELABLE`), and the three tests that cancelled an echoed task now drive a task to `Working` explicitly.
- **`a2acli` never printed the agent's reply (`a2acli`)**: `send`, `get`, and `cancel` printed the task id and `state: TASK_STATE_COMPLETED` and nothing else, though the answer was sitting in `status.message.parts[]` — and the `a2a run` banner tells first-time users to run exactly that command, so a freshly scaffolded agent appeared to do nothing. The status message and any artifact content are now rendered, with non-text parts named in brackets rather than dropped (a file part printed bare is indistinguishable from the agent having said its filename). `stream` gained the same for status and artifact events. States render as `completed` / `input-required` rather than the raw proto name, which belongs on the wire and in `--json`.
- **No `.dockerignore` (workspace)**: the image builds from the workspace root, so `COPY . .` shipped the entire checkout into the build context on every build — 4.9 GB of it, mostly `target/` and the vendored `a2a-mcp/rust-sdk` submodule — including host build artifacts for a different target triple that the builder then ignored and rebuilt. Context is now 5.35 MB and transfers in seconds. Note the patterns are written *without* trailing slashes: Docker matches with Go's `filepath.Match`, where `target/` silently excludes nothing (the first version of this file used trailing slashes and made no difference at all).
- **Agent cards advertised the wrong transport (`a2a-rs`)**: `HttpServer` mounts *only* the ConnectRPC router, but a card built via `SimpleAgentInfo::new` defaulted its primary interface to `JSONRPC`, so every `HttpServer` published a card that lied about itself and card-driven clients negotiated to an endpoint that was never mounted (`invalid JSON-RPC response: error decoding response body`). `HttpServer` now stamps `CONNECTRPC` on the card it serves, and `a2a-agents` sets it at the source for the readers that bypass HTTP — registry self-registration and MCP mode. This unblocked agent-as-tool delegation and skill discovery, both of which rest on that negotiation.

### Added
- **Client-side `Transport` port + JSON-RPC 2.0 client + card-driven negotiation (`a2a-rs`)**: The client gained a hexagonal transport abstraction mirroring the server side, plus a wire-compatible JSON-RPC 2.0 client so it can talk to any standard A2A agent.
  - `port::client::Transport` (re-exported as `a2a_rs::Transport`) is the outbound client port — the renamed, relocated `AsyncA2AClient` with an added `protocol()` discriminator. `HttpClient` (ConnectRPC) reports `"CONNECTRPC"`.
  - `JsonRpcClient` (new `jsonrpc-client` feature) implements `Transport` over the spec JSON-RPC 2.0 wire format (single `POST`, SSE for streaming), reusing the generated ProtoJSON request/response types. Its method names, error codes, and envelopes come from a shared `adapter::transport::jsonrpc_wire` module extracted from the server adapter, so the two directions are byte-compatible (proven by `tests/jsonrpc_client_interop_test.rs`, an in-process client↔server round-trip over a real socket: send/get/list/cancel, push-config CRUD, SSE subscribe, typed error mapping).
  - `TransportFactory` + `TransportNegotiator` + `connect(base_url, &negotiator)` select a transport from an agent card's `supported_interfaces`, ranked by client preference (factory registration order). `default_registry()` prefers CONNECTRPC then JSON-RPC.
